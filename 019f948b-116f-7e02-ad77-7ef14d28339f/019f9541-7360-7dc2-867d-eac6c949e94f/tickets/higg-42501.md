## Real root cause — CONFIRMED
Found by Wellington directly via VS Code debugger running the local API against staging data (`Launch Staging API` launch config, `env/stag`; had to pin `NODE_ENV` explicitly in `.vscode/launch.json` — envFile alone wasn't reliably overriding an already-set process env var). Breakpoint at `ts/managers/msi/index.ts:930`.

**`MsiManager.syncMaterial()`** (`ts/managers/msi/index.ts:922-971`) is the actual auto-sync mechanism called after every MSI custom material save (from `updateMaterial` and 4 other call sites — create/duplicate/remove). This IS the real "Save as Final" trigger.

**The bug — line 930:**
```ts
if (acl.account.corporateReporting && acl.account.flatfileSpaceId) {
```
Gates the ENTIRE sync body (the actual `ImportMsiMaterial.importCustomMaterials` write into the PIC index, marking related products/materials outdated, AND the call to `getAccountFlatfileSpaceOrUpdate` that would lazily create the missing `flatfileSpaceId`) behind `flatfileSpaceId` already being truthy. If it's unset, everything is silently skipped — no log, no error, no job.

**Why it's a real bug, not just missing data:** `getAccountFlatfileSpaceOrUpdate` (`ts/managers/corp-report/bulk-upload-with-flatfile/index.ts:279-349`) already handles provisioning a `flatfileSpaceId` on demand (line 315: `if (!spaceId) { ...create...; account.flatfileSpaceId = spaceId; }`). But it's only reachable from inside `syncMaterial`'s own gate — chicken-and-egg: the function that would create the value is unreachable without already having the value.

**Confirmed on the ticket's staging account** (`v2-staging_accounts-1742241177970` / `667c283415adc5000cbeb9ef`): `corporateReporting: true`, **no `flatfileSpaceId` field at all**.

**Why staging reproduces, dev doesn't:** `flatfileSpaceId` otherwise only gets provisioned via `refreshWorkBook()` (Product Library "Sync"/"Refresh Workbook" UI button) or a bulk `updatePicProductsAccountShares` job — neither is part of normal account onboarding. A personal dev account used for general testing has likely hit that button at least once. The staging QA account (`667c283415adc5000cbeb9ef`) was created narrowly for this ticket's repro and never touched that other flow — so it never got a `flatfileSpaceId`, and `syncMaterial` has silently no-op'd for it ever since. Account-history divergence, not an environment/infra divergence.

## Fix — NOT YET IMPLEMENTED, pending discussion
Likely direction: don't gate the whole `syncMaterial` body on pre-existing `flatfileSpaceId` — let `getAccountFlatfileSpaceOrUpdate` provision it lazily as it already supports, and/or log a warning when `corporateReporting` is true but `flatfileSpaceId` is missing so this never fails silently again. Needs a regression test: account with `corporateReporting: true` + no `flatfileSpaceId` saving an MSI custom material should still sync.
